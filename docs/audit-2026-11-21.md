Scope: full-project audit requested while the operator slept, on top of the combo-failover work
landed in `3d87be4` → `ae9a21e` → `f49c9ad`. Two auditors ran (relay core; dialects/panel/OAuth/

## Live incident first: the 422 that broke streaming clients

**Symptom.** A client (the operator's own coding agent) sending the OpenAI `developer` role
through the `mistral-large` combo got `422` from `api.mistral.ai`:

```
Input tag 'developer' found using 'role' does not match any of the expected tags:
<Roles.system>, <Roles.user>, <Roles.assistant>, <Roles.tool>
```

The combo's first step (`mistral-vibe-api`) and second step (`mistral-api`, plain `open-ai`
dialect) both rejected it, the chain retried once (`max_retries: 1`), and the client saw the
upstream 422.

**Root cause.** Both steps speak the OpenAI wire and are served as passthrough: the client's
bytes are forwarded untouched. The OpenAI spec's `developer` role (the newer name for `system`)
is accepted by the relay but not by Mistral's pydantic schema, which knows only
`system | user | assistant | tool`.

**Fix** (`normalize_developer_role`, `crates/manarouter-relay/src/server.rs`): on every
passthrough body, `messages[].role == "developer"` is rewritten to `system` before the request
leaves — except when the upstream is a real OpenAI host (`api.openai.com`), where the role is
meaningful and accepted as sent. The rewrite runs only when a role actually changes, so bodies
without the alias are still byte-for-byte. Pinned by
`a_developer_role_reaches_a_prerename_upstream_as_system` (the upstream sees `system`, the user
message untouched) and `a_body_without_a_developer_role_is_not_reencoded` (a provider-specific
field survives verbatim).

**Verified live** against the running relay after deploy: a `developer`-role request through
`mistral-vibe-api/zai-glm-5-3-flash` and through the `mistral-large` combo both return `200`
with real completions, and the logs show a single-step serve with no failover.

**Also fixed while here:** the patience-loop's failover log used to claim "failing over past
the rate limit" for *any* tried state — including successes and ordinary 4xx — because the
`later_available` break sat at the top of the loop before the attempt was classified. The
breakout now only fires for states the hold could absorb, and the message names the actual
cause (`resource-exhausted refusal...` / `status = 422` / `every account ... cooling down`).

## Open question left for the operator

**`mistral-vibe-api` account `api-key` has no `secret_ref`.** The provider holds three accounts
(`api-key`, `account-2`, `vibe-cli-key`); the first carries no `secret_ref` at all, so it can
never authenticate. Separate 401 `{"detail":"Invalid API Key"}` responses from
`api.mistral.ai` were logged (02:53, 03:10, 04:00) on this provider. Auth-failure cooldowns
(900 s) self-heal these, and the combo verified `200` end-to-end after deploy, but the
operator should either give that account a real key or remove it. Not done automatically:
account credentials are the operator's data.

## Audit findings — relay core (static review, `f49c9ad` + working tree)

Reviewed: `server.rs` (failover loop, attempt/sweep machinery, reset parsers), `select.rs`,
`account_spend.rs`, `upstream.rs`, `recovery.rs`, `state.rs`, `quota.rs`, and the mr-core
`dialect`/`model`/`snapshot`/`account_quota`/`config` modules.

**Verdict: no defects found in the targeted logic.** Specifically verified clean:

- The `'patience` failover loop: entered only for absorbable states; every arm exits by a
  guarded `continue` (budget resets) or an explicit `break`; the failover messages match the
  states that reach them.
- `select.rs`: `order_steps_with` partitions stably and sorts only the unavailable tail, so
  healthy steps can never be demoted; `step_has_usable_account_if` takes the spend predicate
  by reference (no lifetime capture); health views are re-read per attempt.
- Reset parsing: depth-bounded walk, numeric-leaf-only, ms/second denomination normalized,
  past instants yield no park, 24 h ceiling holds.
- `account_spend.rs` ticket lifecycle: idempotent settle, drop-settle, re-measure path.
- `recovery.rs` wrap/replay: no defects surfaced.

## Audit findings — dialects, panel, OAuth, catalog

### Fixed the same night

1. **Panel "Mistral Vibe" preset pointed at the wrong host** (`panel/view-providers.js`): the
   preset and `DIALECT_BASE_URLS` said `https://api.mistral.ai/v1`, but the `mistral-vibe`
   dialect (LeChat) speaks to `https://chat.mistral.ai` — a panel-created Vibe provider could
   never work. → Fixed to `https://chat.mistral.ai`. (This also explains the observed 401
   `Invalid API Key` from `api.mistral.ai` for pre-set-created providers.)
2. **The repo's own drift-guard test was failing at HEAD** (`panel/test/provider-presets.test.mjs`):
   three drifts behind one assertion — Codex preset missing `chat`, the Vibe preset's wrong
   base URL, and the Vibe preset claiming `responses`/`tool-calling` the dialect does not
   implement. → All three fixed; suite now 406/406.
3. **Panel Codex preset omitted `chat`** — a panel-created Codex provider refused
   `/v1/chat/completions` at the capability gate. → Added.
4. **Mistral Vibe OAuth classified every token-endpoint failure as transient**
   (`crates/mr-core/src/oauth/mistral_vibe.rs`): a revoked/expired session would retry forever
   and never surface "log in again". → Both the exchange and refresh paths (and userinfo) now
   go through the shared `endpoint_failure` classifier, matching every other platform.
5. **The settings panel read the wrong key for `debugLogMessages`**
   (`panel/view-settings.js`): the API serializes the camelCase serde name, the panel read the
   snake_case alias, so the toggle always showed off — and saving silently disabled an enabled
   debug log. → Reads and writes `debugLogMessages`.
6. **Panel Antigravity preset used the wrong host** (`cloudcode-pa` vs the catalog's
   `daily-cloudcode-pa`, whose absence fails inference in ways that look like quota
   exhaustion). → Aligned with the catalog.
7. **Vibe translation 400'd on array-shaped content** (`crates/mr-dialects/src/vibe.rs`):
   the OpenAI SDKs wrap plain text in `[{"type":"text","text":…}]` for multimodal-capable
   models; the prompt extractor only accepted string content, so ordinary clients got
   `400 no user text message found`. → Text parts are flattened; only genuinely empty input
   is refused.
8. **Vibe stream translation froze on shrinking text** (`emit_content_delta`): patches are
   replacement-semantics but the delta emitter only ever emitted growth, so a rewrite that
   shortened an earlier chunk never reached the client. → A shrink now emits the corrected
   text (on a new line, since OpenAI deltas concatenate).

### Also done

9. **Mistral Vibe requests forward the client's own User-Agent** — now forced to the desktop
   app's UA for the LeChat dialect, matching the module's own fingerprint contract.
10. **Mistral Vibe refresh assumed a fresh `id_token`** — when Ory's refresh response omits
    one, the previous id token is now carried forward instead of falling back to the opaque
    access token the LeChat gateway rejects.
11. **Dependency hygiene** — removed eight unused crate dependencies (`anyhow`, `socket2`,
    `smallvec`, `memchr` from mr-core; `http`, `futures-util`, `async-trait`, `tracing`,
    `smallvec` from mr-dialects) and a redundant dev-dependency `tempfile`.

### Noted, deliberately not changed

- `mistral_vibe::API` (`crates/mr-core/src/published.rs`) is unreferenced; it documents the
  platform API origin the `mistral-vibe-api` dialect actually uses, so it stays.
- The `debugLogMessages` setting itself works as designed (default off, logs admitted requests
  with timestamps to the relay journal when on).
- The `mistral-vibe` (LeChat) translation keeps its documented "last user message only"
  shape; advertising tools on it would be wrong, and the preset no longer claims them.
